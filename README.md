# Exoplanet Transit Detection | Python to FPGA/ASIC Acceleration

Exploring the intersection of **astronomy, signal processing, and digital hardware design** through an initial software baseline for exoplanet transit detection.

The project begins with a synthetic stellar light curve and a simplified Box Least Squares (BLS)-style search. The planned next stages include validation against established algorithms, analysis of real Kepler/TESS observations, and exploration of FPGA prototyping and ASIC-oriented design-space analysis.

> **Current status:** Initial synthetic-data experiment completed. Real astronomical data validation is planned.

## Project Overview

An exoplanet can sometimes be detected when it passes in front of its host star, causing a small, periodic decrease in the star's observed brightness. This phenomenon is called a *transit*.

Detecting these small brightness dips in noisy stellar measurements is a computational challenge.

This project investigates a software-to-hardware workflow for transit detection, with an eventual focus on computational efficiency and hardware implementation.

### Current objectives

- Generate a synthetic stellar light curve containing a known periodic transit.
- Implement an initial BLS-style period-search algorithm in Python.
- Evaluate how closely the detected orbital period matches the injected period.
- Establish a software reference for future algorithm validation.
- Investigate real astronomical observations from NASA's Kepler and TESS missions.
- Explore FPGA acceleration and ASIC-oriented design-space analysis.

## Current Implementation

The current Python baseline generates a synthetic light curve with an injected transit signal and Gaussian noise.

The search evaluates candidate orbital periods and transit durations, then selects the candidate with the strongest score according to the implemented transit-window scoring method.

**Important:** This is an educational, simplified BLS-style implementation. It is not yet a validated scientific BLS pipeline.

## Initial Results — Synthetic Data

The first experiment used a simulated stellar light curve with a known injected transit.

| Parameter | Value |
|---|---:|
| Number of observations | 1,350 |
| Observation span | 27 days |
| Trial periods | 400 |
| Trial durations | 5 |
| Injected orbital period | 3.70000 days |
| Detected orbital period | 3.69424 days |
| Absolute period error | 0.00576 days |
| Relative period error | Approximately 0.156% |
| Injected transit depth | 1.000% |
| Estimated transit depth | 0.922% |
| Search runtime | Approximately 7.03 seconds |

### Interpretation

The simplified search recovered an orbital period close to the injected value in this synthetic experiment.

The estimated transit depth also approximated the injected depth. Differences can arise from noise, sampling, and the implementation's simplified scoring and estimation procedure.

These results demonstrate an initial proof of concept on controlled synthetic data. They do **not** establish detection performance on real astronomical observations or demonstrate superiority over existing methods.

The reported runtime is specific to the Python environment used for this experiment. It is not a prediction of FPGA or ASIC performance.

## Getting Started

### Requirements

- Python 3.10 or later recommended
- NumPy
- Matplotlib (optional, for plotting)

### Installation

Clone the repository:

```bash
git clone https://github.com/YOUR_USERNAME/exoplanet-transit-detection-fpga-asic.git
cd exoplanet-transit-detection-fpga-asic
```

Install the dependencies:

```bash
pip install -r requirements.txt
```

Run the baseline:

```bash
python exoplanet_bls_baseline.py
```

The script generates a synthetic light curve, performs the period search, prints the detection metrics, and saves its outputs.

Replace `YOUR_USERNAME` with your GitHub username when using the clone command.

## Real Astronomical Data — Planned

The next stage is to validate the software workflow using actual stellar light curves.

### Planned data sources

**NASA Mikulski Archive for Space Telescopes (MAST)**  
https://archive.stsci.edu/

Provides access to Kepler and TESS mission observations.

**NASA Exoplanet Archive**  
https://exoplanetarchive.ipac.caltech.edu/

Provides published exoplanet parameters that can be used to check detected candidates against known planets.

### Planned validation workflow

1. Select a suitable target with available stellar observations.
2. Download its light-curve data.
3. inspect and prepare the observation times and flux measurements.
4. Run the detection algorithm on the observed data.
5. Compare recovered periods against published planetary parameters where applicable.
6. Validate the implementation against a trusted BLS algorithm.
7. Conduct injection-recovery experiments using artificial transits inserted into real light curves.

Real-data validation has not yet been completed in the current version of this project.

## FPGA and ASIC Research Direction

Following software validation, the longer-term direction is to investigate whether computationally intensive parts of the transit search can be mapped efficiently to digital hardware.

Potential hardware blocks include:

- Observation input and buffering
- Candidate-period control
- Phase calculation and phase folding
- Transit-window statistics
- Candidate scoring and top-candidate selection
- Fixed-point arithmetic and parallel processing
- Host-to-FPGA data transfer, potentially using AXI4-Stream

### Planned hardware evaluation

Potential metrics include:

- Detection accuracy and period-recovery error
- Throughput and latency
- FPGA LUT, flip-flop, DSP, and BRAM utilization
- Maximum clock frequency and timing slack
- Power and energy, where reliable measurement or estimation is available
- ASIC standard-cell area, timing, and power estimates after synthesis

These are planned investigations, not measured hardware results. No FPGA or ASIC implementation results are claimed in this initial release.

## Research Questions

1. How closely can a hardware-oriented transit-search implementation reproduce a validated software reference?
2. How do fixed-point precision and parallelism affect detection quality and computational efficiency?
3. How reliably can shallow transit signals be recovered as noise increases?
4. What are the trade-offs between detection performance, throughput, latency, and hardware resources?
5. Can the approach be validated across observations from different space-telescope missions?

The specific research contribution will be refined after reviewing related scientific algorithms and existing hardware-acceleration work.
